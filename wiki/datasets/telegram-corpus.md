# Telegram-корпус — цільові дані проєкту

> 🔁 **Це замінює попереднє припущення проєкту.** Раніше вважалося, що цільові дані —
> україномовні. Насправді: **записи з Telegram, ~2 ТБ, нерозмічені, здебільшого
> російськомовні**. Перша задача — не ідентифікація, а **кластеризація**
> ([[concepts/speaker-clustering]]).

## Що відомо

| Параметр | Значення |
| :-- | :-- |
| Джерело | Telegram (голосові повідомлення / аудіо) |
| Обсяг | **~2 ТБ** |
| Розмітка | **відсутня повністю** — немає JSON-експорту, лише .ogg файли |
| Залізо | **4 × RTX 4090** (~96 ГБ VRAM) |
| Контекст | дослідження |
| Мова | здебільшого **російська** |
| Перша задача | кластеризація за мовцями |

## Скільки це в годинах — залежить від формату

| Якщо дані зберігаються як | Байт/с | Годин у 2 ТБ | Повідомлень (по ~15 с) |
| :-- | --: | --: | --: |
| WAV 16 кГц / 16 біт / mono | 32 000 | **~17 000** | ~4 млн |
| OPUS ~24 кбіт/с | 3 000 | ~185 000 | ~44 млн |
| OPUS ~16 кбіт/с | 2 000 | ~278 000 | ~67 млн |

Розкид у **16 разів** → це перше, що треба з'ясувати ([[open-questions]] №24).

Для масштабу: **VoxCeleb2-dev — ~2 400 годин, 5994 диктори**. Навіть нижня оцінка
(17 тис. годин) — це в 7 разів більше за корпус, на якому натреновані всі моделі
з [[models/comparison]]. Верхня оцінка виглядає нереалістичною для самих лише
голосових повідомлень → ймовірно, 2 ТБ включають відео/фото/документи.

## Технічні особливості формату

- **OPUS в контейнері OGG**, mono — стандарт голосових повідомлень Telegram.
  Точний бітрейт і ефективну смугу треба виміряти на власних файлах, не припускати.
- **Однорідний кодек-ланцюг** — на відміну від «мікрофон + телефон + диктофон»,
  тут усі записи пройшли через один і той самий кодек. Для
  [[concepts/domain-mismatch]] це **добра новина**: канальна варіативність нижча,
  ніж у типовому «дикому» корпусі.
- **Мікрофон смартфона**, часто в русі, з фоновим шумом.
- **Короткі записи** — багато повідомлень на 3–15 с, частина коротша за 3 с
  (нижче порога надійності ембедингів, див. [[concepts/audio-preprocessing]]).
- **Не все є мовленням**: музика, меми, звукові ефекти, пересилання.
- **Дублікати** — пересилання того самого файлу. Дедуплікація до обробки може
  суттєво скоротити корпус.

## ❌ Метаданих немає (уточнено 2026-08-27)

> Попереднє припущення про JSON-експорт з `from_id` **не підтвердилось**.
> Це просто тека з .ogg-файлами без прив'язок. Ідея «безкоштовна DET-крива з
> метаданих відправника» **знята**.

Наслідок: калібрувати поріг доводиться **без жодних міток**. Замінники —
[[concepts/speaker-clustering]], розділ «Калібрація без міток»:
split-half позитиви + випадкові пари як негативи + маленький вручну розмічений
набір пар у зоні невизначеності.

### Що ще може лишитись структурою (перевірити)

Навіть без JSON у файлів може бути залишкова структура — і вона варта перевірки
**до** будь-якої обробки:

| Сигнал | Що дає |
| :-- | :-- |
| **Тека = чат** (експорт Telegram Desktop кладе voice_messages по чатах) | у діалозі 1:1 усі голосові — від **двох** людей. Це дуже сильне обмеження для кластеризації |
| **Timestamp в імені файлу** | часова близькість усередині чату = репліки одної розмови |
| **Дублікати / пересилання** | пари «те саме аудіо» — ідеальні позитиви |
| Порядок / нумерація файлів | послідовність розмови |

Якщо теки відповідають чатам — це майже повертає втрачену слабку розмітку,
хоч і на рівні «група з N людей», а не «конкретний відправник».

## Залізо

**4 × RTX 4090** змінює баланс задачі:

- витяг ембедингів перестає бути вузьким місцем (порядок годин на весь корпус);
- вузьке місце — **декодування OPUS і I/O по мільйонах дрібних файлів** (CPU + диск);
- 96 ГБ VRAM робить реальним **власне тренування енкодера на цьому ж корпусі** —
  див. [[concepts/pseudo-label-training]]. Це найцінніше застосування такого заліза.

## Наслідки для решти wiki

- **Задача**: кластеризація, не watchlist-ідентифікація → [[concepts/task-types]].
- **Мова**: російська, не українська → доказ «ResNet виграв на українських даних»
  ([[sources/pretrained-models-review]]) лишається дотичним (слов'янська мова),
  але вже не прямим.
- **Масштаб**: 2 ТБ дрібних файлів — саме та проблема, яку вирішує **UIO**
  (tar-шарди) з [[sources/wespeaker-toolkit]].
- **Управління даними**: біометрична обробка персональних даних реальних людей.
  Впливає на дизайн (чи зберігати сире аудіо, чи лише ембединги; ретенція;
  псевдонімізація) → [[open-questions]] №28.
