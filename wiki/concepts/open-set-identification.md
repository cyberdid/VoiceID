# Open-set ідентифікація і «false-alarm problem»

**Найважливіше практичне поняття проєкту** — і те, про яке мовчать усі описи моделей.

## Постановка

Є **watchlist** — список заздалегідь зареєстрованих (enrolled) мовців. Приходить запис.
Треба вирішити: він від когось зі списку (**in-set**) чи від стороннього (**out-of-set, OOS**).

```
запис → енкодер → ембединг → cosine similarity з КОЖНИМ у watchlist
      → s* = max_i {s_i}
      → s* ≥ θ  →  in-set (і це мовець i)
      → s* < θ  →  out-of-set
```

Два типи помилок:
- **false reject (FRR)** — свого не впізнали;
- **false alarm (FAR)** — чужого зарахували до списку.

## Проблема

Оператор `max` над watchlist — це джерело біди. Чим більше людей у списку, тим більше
шансів, що **хоч один** дасть високий скор випадково. Розподіл OOS-скорів **зсувається
вправо** зі зростанням watchlist → перекривається з in-set → **FAR росте при фіксованому порозі**.

### Кількісно (ResNet-34, [[sources/voxwatch-osi-benchmark]])

Watchlist 50 → 500:

| Метрика | 50 | 500 | Зміна |
| :-- | --: | --: | :-- |
| FAR@FRR=5% | 2,4% | **16,1%** | у ~7 разів гірше |
| FRR@FAR=0,5% | 10,1% | **21,1%** | більш ніж удвічі |

Це **та сама річ**, яку [[sources/pretrained-models-review]] описує якісно:
«чим більше записів із голосами різних осіб, тим більше схожих голосів, тому зі
збільшенням обсягу падає точність — можливо, потрібно буде розділяти дані на порції».
VoxWatch дає цьому число.

Для порівняння: іризна біометрія працює з watchlist на мільйон суб'єктів при дуже
низькому FAR. Тобто це специфічна слабкість **голосової** біометрії, а не біометрії взагалі.

## Що з цим робити

За [[sources/voxwatch-osi-benchmark]], за спаданням ефективності:

1. **Score fusion** двох систем — −44% FAR при watchlist 1210. Найдешевше.
2. **Score calibration (QMF)** — −21% FAR на всіх розмірах watchlist.
3. **Сильніший енкодер** — працює, але має межу при фіксованих розмічених даних.
4. **AS-Norm** — ⚠️ **не гарантія**: допомагає слабким моделям, сильним може шкодити.
5. **Довші сегменти** — 30 с enroll / 30 с test; далі різке спадання віддачі.

Деталі — [[concepts/score-normalization]].

## Практичний висновок для проєкту

**Розмір бази — це параметр якості, а не деталь реалізації.** Питання «яку модель взяти»
має сенс лише разом із питанням «скільки людей у базі». Система, що дає 2,4% FAR на 50
дикторах, дасть 16% на 500 — без жодної зміни в моделі.

Тому [[experiments/protocol]] обов'язково міряє якість **як функцію розміру watchlist**,
а не одним числом.
