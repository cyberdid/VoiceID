# VoiceID — схема wiki

Цей проєкт побудований за патерном **LLM Wiki** (Andrej Karpathy,
<https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f>).
Знання не «перевідкриваються» при кожному питанні — вони **компілюються один раз
і підтримуються в актуальному стані**.

## Предмет

**Large-Scale Open-World Speaker Discovery and Identification** у неоднорідному масиві ~3 TB аудіо (російська, українська, суржик, code-switching).
- **Головне джерело правди (SSOT):** `docs/VOICE_ID_OPENEVOLVE_MASTER.md` та `[[master-context]]`.
- **Рушій еволюції алгоритмів:** `OpenEvolve` (`algorithmicsuperintelligence/openevolve`).
- **Дослідницька платформа:** `VoiceEvolve`.
- **Базовий енкодер:** `ReDimNet2` (`ReDimNet2-B6` для продакшну, `B3` для експериментів).
- **Залізний закон:** «False merge набагато гірший за false split».

Робоча теза та синтез — у [[overview]].

## Шари проєкту

| Шар | Де | Хто пише |
| :-- | :-- | :-- |
| **Master Context (SSOT)** | `docs/VOICE_ID_OPENEVOLVE_MASTER.md` / `wiki/master-context.md` | Головна технічна специфікація проєкту. |
| **Raw sources** | `docs/` | **Людина.** Незмінні. Агент лише читає, ніколи не редагує і не видаляє. |
| Веб-дослідження | `wiki/sources/lit-*.md` | **Агент.** Літературні довідки з веб-пошуку. Frontmatter: `raw: web`, `retrieved:`, `confidence:`. |
| **Wiki** | `wiki/` | **Агент.** Повністю. Людина читає й спрямовує. |
| **NotebookLM Export** | `notebooklm/` | **Агент.** Зведені тематичні досьє для Google NotebookLM (Gemini RAG). |
| **Схема** | `CLAUDE.md` (цей файл) | Спільно, еволюціонує з часом. |
| Робочий смітник | `temp/` | Будь-що тимчасове. Не є частиною wiki. |

`docs/` = шар raw sources. Не перейменовувати без прямого прохання.
`notebooklm/` = шар експорту та інтеграції з Google NotebookLM.

## Структура wiki

```
wiki/
├── index.md          ← каталог усіх сторінок (оновлювати при КОЖНОМУ ingest)
├── log.md            ← хронологічний append-only журнал
├── overview.md       ← синтез: що ми знаємо, робоча теза, рекомендований шлях
├── open-questions.md ← відкриті питання, прогалини, що робити далі
├── sources/          ← по одній сторінці на кожне джерело з docs/
├── models/           ← сторінки-сутності: одна модель (або сімейство) = одна сторінка
├── concepts/         ← поняття: EER, ембединг, open-set, score normalization…
├── datasets/         ← датасети
└── experiments/      ← протокол оцінювання та результати НАШИХ прогонів
```

## Конвенції сторінок

- **Мова:** українська. Технічні терміни лишаємо англійською в дужках при першій згадці:
  «ембединг мовця (speaker embedding)». Назви моделей, метрик, бібліотек — як в оригіналі.
- **Імена файлів:** `kebab-case.md`, латиницею (щоб не ламати shell-інструменти).
- **Frontmatter** (YAML) обов'язковий — під нього працює Dataview в Obsidian:
  ```yaml
  ---
  type: model | concept | source | dataset | experiment | overview
  tags: [ключові, слова]
  sources: [slug-джерела, ...]   # звідки взято факти цієї сторінки
  status: candidate | rejected | verified | untested   # для моделей
  updated: YYYY-MM-DD
  ---
  ```
- **Посилання:** `[[slug-сторінки]]` (Obsidian wikilinks). Посилатися щедро.
  Посилання на ще неіснуючу сторінку — це нормально: це нотатка «варто написати».
- **Кожен факт має походження.** У кінці сторінки — секція `## Джерела` з посиланнями
  на `[[sources/...]]`. Твердження без джерела позначати як `(висновок агента)`.
- **Суперечності не згладжувати.** Якщо два джерела кажуть різне — окремий блок
  `> ⚠️ **Суперечність:**` прямо на сторінці + рядок в [[open-questions]].
- **Числа з джерел копіювати точно**, разом з умовами вимірювання (датасет, тривалість,
  поріг). EER без вказання тесту — марне число.

## Операції

### Ingest (нове джерело)

Людина кладе файл у `docs/` і каже «заінджесть».

1. Прочитати джерело **повністю** (PDF — `pdftotext`, ноутбуки — розпарсити і код, і **outputs**).
2. Коротко обговорити з людиною ключові висновки, перш ніж писати.
3. Створити `wiki/sources/<slug>.md` — конспект: що це, що стверджує, які числа, які вади.
4. **Оновити зачеплені сторінки** в `models/`, `concepts/`, `datasets/` — не лише додати,
   а й переглянути старі твердження, які нове джерело підсилює або спростовує.
5. Оновити [[index]] і, якщо змінилася теза, [[overview]].
6. Дописати рядок у [[log]].

Одне джерело зазвичай зачіпає 5–15 сторінок. Це нормально.

### Query (питання)

1. Спочатку прочитати [[index]] → знайти релевантні сторінки → тільки тоді читати їх.
2. Відповідати **з посиланнями на сторінки wiki**, а не з пам'яті.
3. **Хороша відповідь — це нова сторінка.** Порівняння, аналіз, знайдений звʼязок —
   зафайлити у wiki (зазвичай у `concepts/` або `experiments/`), а не лишати в чаті.
4. Дописати рядок у [[log]].

### Research (веб-дослідження)

Коли в корпусі `docs/` є діра, а питання важливе — шукати в мережі і **файлити
результат як `wiki/sources/lit-<тема>.md`**. Обов'язково:
- `raw: web` + `retrieved: YYYY-MM-DD` + поле `confidence:` у frontmatter;
- чесно зазначати, що прочитано: анотації пошуку чи повні PDF;
- числа з анотацій позначати як орієнтир, не як цитату;
- далі — звичайний ingest: оновити зачеплені сторінки, [[index]], [[log]].

### Lint (перевірка здоровʼя)

Періодично, на прохання: шукати суперечності між сторінками; застарілі твердження,
які перекрито новішим джерелом; сторінки-сироти без вхідних посилань; поняття, які
згадуються, але не мають своєї сторінки; відсутні перехресні посилання; прогалини в
даних, які можна закрити веб-пошуком. Результат — оновлений [[open-questions]] + запис у [[log]].

### Experiment (наш власний прогін)

Коли щось реально запускається (модель, бенчмарк, fine-tune):
`wiki/experiments/YYYY-MM-DD-<slug>.md` з полями: **гіпотеза → дані → конфіг →
метрики → висновок → що далі**. Обов'язково фіксувати seed, версії, тривалості аудіо
й пороги. Протокол — [[experiments/protocol]].

## Формат журналу

`wiki/log.md` — append-only, кожен запис починається однаково, щоб грепалося:

```
## [YYYY-MM-DD] ingest | Назва джерела
## [YYYY-MM-DD] query | Питання
## [YYYY-MM-DD] lint | Що перевірено
## [YYYY-MM-DD] experiment | Що запущено
```

Останні записи: `grep "^## \[" wiki/log.md | tail -5`

## Чого не робити

- Не редагувати й не видаляти нічого в `docs/`.
- Не писати вміст у `index.md` — там лише каталог: посилання + один рядок опису.
- Не вигадувати числа. Якщо метрика невідома — писати `—` і додавати рядок в [[open-questions]].
- Не переносити «заявлений розробниками EER» у наші висновки як факт: він міряний на
  різних тестах і не на українських даних. Див. [[concepts/eer-and-metrics]].
